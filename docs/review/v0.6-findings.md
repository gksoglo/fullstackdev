# Review of PRD v0.6 + Implementation Roadmap — Findings & Errata

Source reviewed: `prd_n_roadmap.docx` — *Product Requirements Document — HTF/LTF
Trend-Continuation EA, Draft v0.6* plus the companion *Implementation Roadmap*.

Review goal, taken from the document's own stated design objective: *"two independent
implementations of this specification, given the same market data and parameters, should
produce the same structural interpretation and the same trades."* Every finding below is
scored against that bar — a gap is only "blocking" if two competent implementers could
read the same sentence and legitimately build different behaviour.

All fixes are applied in `docs/prd.md` (v0.7) and `docs/roadmap.md`.

Severity key:

| Level | Meaning |
|---|---|
| **B — Blocking** | Two implementations will diverge, or the EA is provably wrong / will crash. |
| **M — Material** | Ambiguous or self-contradictory; needs a decision before coding. |
| **E — Editorial** | Dangling reference, numbering gap, or wording defect. No behavioural risk. |

---

## Summary

23 findings: **6 blocking**, **10 material**, **7 editorial**.

The two most serious are **B-1** (momentum classification is not direction-aware, so
every short trade that is working is classified `NEGATIVE` and rejected) and **B-2**
(the position-size formula omits tick-value conversion and does not yield lots). Either
one alone is sufficient to reproduce the "zero trades across multiple backtests" failure
that the roadmap was written to prevent — B-1 silently zeroes the entire short side of
the funnel, which is exactly the class of bug the Stage 7 funnel line is meant to expose.

## Blocking findings

### B-1 — §12 Momentum classification is not direction-aware; all short entries reject

§12.4 defines ROC as a signed close-to-close percent return:

```
ROC = (Close[0] − Close[ROC_Period]) / Close[ROC_Period] × 100
```

§12 then classifies on the raw signed value:

```
STRONG:   ROC >= ROC_STRONG_THRESHOLD
NEGATIVE: ROC <= ROC_NEGATIVE_THRESHOLD
```

For a **short** setup, a healthy bearish impulse produces a large *negative* ROC. Under
the rule as written that is classified `NEGATIVE → REJECT`. The stronger the bearish
momentum, the more certain the rejection. Conversely a short entering into a rally is
classified `STRONG` and gets the *higher* risk allocation.

§24 ("Short Entry Algorithm — Mirror of §23") does not rescue this: mirroring an entry
algorithm does not tell an implementer to negate a ROC threshold comparison, and the two
thresholds are not symmetric about zero, so "flip the signs" is not a well-defined
mirror either.

**Consequence:** the short side of the funnel is ~100% `momentum_reject`. This is a
silent, plausible-looking failure — the funnel counter shows a populated pipeline right
up to Stage 7 and then zero short entries, with no external symptom.

**Fix (§12.1, v0.7):** classify on a **direction-signed** value:

```
Directional_ROC = +ROC   for a long setup
Directional_ROC = −ROC   for a short setup
```

All three tiers compare against `Directional_ROC`. Thresholds keep one meaning
("momentum in the direction of the intended trade") for both directions, and
`ROC_NEGATIVE_THRESHOLD` stays a small negative number for both. Raw signed `ROC` is
still what gets written to the trade log (§26), with `Directional_ROC` logged alongside.

### B-2 — §15 Position-size formula does not produce lots

```
Position size = Account_Risk / |Entry − Initial_SL|
```

`Account_Risk` is account currency; `|Entry − Initial_SL|` is a price difference. The
quotient is "currency per unit of price", not a lot count. The value is only accidentally
close to correct on an instrument where one lot moves one currency unit per one price
unit. On FX, metals, indices and anything with a `TickValue`/`TickSize` ratio other than
1 it is wrong by a large constant factor, in either direction.

**Fix (§15, v0.7):** full conversion, then broker-constraint normalisation:

```
StopDistancePrice = |Entry − Initial_SL|
StopDistanceTicks = StopDistancePrice / SYMBOL_TRADE_TICK_SIZE
RiskPerLot        = StopDistanceTicks × SYMBOL_TRADE_TICK_VALUE
RawLots           = Account_Risk / RiskPerLot
Lots              = floor(RawLots / LotStep) × LotStep, clamped to [MinLot, MaxLot]
```

with an explicit rule for what happens when `Lots < MinLot` (reject the trade and count
`REJECT_position_size`; never silently round up to `MinLot`, which would over-risk the
account), and a guard for `RiskPerLot <= 0`.

### B-3 — §7.1 ER divides by zero on a flat window

```
ER = |Close[0] − Close[N]| / Σ(i=1 to N) |Close[i-1] − Close[i]|
```

If every close in the window is identical the denominator is exactly `0.0`. This is not
hypothetical: it happens on illiquid symbols, on frozen feeds, on holiday sessions, and
in any synthetic test fixture built from a constant series. In MQL5 this yields `inf` or
`nan`, which then propagates silently through `REGIME_STATE` — `nan` compares `false`
against both `ER_HIGH` and `ER_LOW`, so the symbol lands in the ambiguous band and the
regime is decided entirely by ADX, with no log line saying why.

**Fix (§7.1, v0.7):** define `ER = 0.0` when the denominator is zero, which classifies
the window as `CHOPPY` — the correct and safe interpretation of "no movement at all".
Also state the data-sufficiency precondition explicitly: ER requires `N + 1` completed
HTF candles; before that `REGIME_STATE = CHOPPY` (insufficient data), never a partial sum.

### B-4 — §35 forbids parameter sharing while §11.3/§13 share `MinimumPoints`

§35 states, in bold terms: *"Never share a parameter or calculation, despite the same
formula shape."* But `MinimumPoints` — a single, un-suffixed identifier — appears in both:

```
§11.3  BOS_Break_Distance = max(MinimumPoints, LTF_ATR × BOS_ATR_Multiplier)
§13    SL_Buffer          = max(MinimumPoints, LTF_ATR × SL_ATR_Multiplier)
```

This directly contradicts the section that exists to prevent exactly this. It also
couples two floors that must be tuned against different things: the BOS floor guards
against noise breaks, the SL floor guards against broker stop-distance and spread.

**Fix (§35, v0.7):** three distinct parameters — `BOS_MinimumPoints`,
`SL_MinimumPoints`, `Structural_MinimumPoints` — and §35's disambiguation table extended
to list the floor alongside the multiplier for each of the three buffers.

### B-5 — §5.2/§5.3 use `Structural_Break_Buffer` with no formula anywhere

§5.2 and §5.3 invalidate structure against `Protected_Low − Structural_Break_Buffer`.
§35 says the buffer is "HTF_ATR-scaled". No section states the actual expression, and no
multiplier parameter for it exists in §32 or in §38's validation list — while every other
ATR multiplier in the document (`BOS_ATR_Multiplier`, `SL_ATR_Multiplier`,
`TrailATRMultiplier`, `TrailShadowMultiplier`) is both named and validated.

Two implementers will pick different things here: a fixed point value, `1.0 × HTF_ATR`,
or a multiplier they invent. Structure invalidation sensitivity is the single highest
zero-trade risk factor in the whole build per the roadmap's own summary table, so an
unspecified constant sitting inside it is a serious gap.

**Fix (§5.4, v0.7):**

```
Structural_Break_Buffer = max(Structural_MinimumPoints,
                              HTF_ATR × Structural_Break_ATR_Multiplier)
```

with `Structural_Break_ATR_Multiplier` added to §32's parameter table and to §38's
`<= 0` validation list.

### B-6 — §16.4 `Average_LTF_Shadow` is undefined

The trailing-stop formula depends on it:

```
TrailDistance = max(Average_LTF_Shadow × TrailShadowMultiplier, LTF_ATR × TrailATRMultiplier)
```

Nothing in the document says which shadow (upper, lower, or both), over how many bars,
on which timeframe, or whether the still-forming bar is included. Every one of those is a
free choice that changes the trailing distance, and therefore changes exit prices and
realized R on every trailing exit.

**Fix (§16.4, v0.7):** explicit definition — the mean, over the last
`ShadowLookbackBars` **completed** LTF bars, of the shadow **on the side the trade is
trailing from** (upper shadow `High − max(Open, Close)` for longs; lower shadow
`min(Open, Close) − Low` for shorts), with `ShadowLookbackBars` added to the parameter
table and to §38 (`< 1` rejected).

## Material findings

### M-1 — §22.2 and §23 specify two different pipeline orders

| §22.2 (Evaluation pipeline) | §23 (Long Entry Algorithm) |
|---|---|
| 1. Session | position already open |
| 2. Spread | bar just closed a position |
| 3. Daily risk | daily risk |
| 4. Cooldown | cooldown |
| 5. Frozen HTF snapshot | session |
| 6. Structure | spread |
| … | … |

Both claim to be normative, and they disagree on the order of four gates. This is not
cosmetic: the funnel counter attributes each rejected bar to *the first gate that
rejects it*, so the two orders produce different funnel breakdowns from identical data —
defeating the counter's entire diagnostic purpose. §22.2 also omits the position-open and
same-bar-close guards that §23 has.

**Fix:** §22.2 is made the single normative order, extended with steps 0a/0b for the two
position guards, and §23 is rewritten to follow it exactly. The roadmap's funnel listing
is reordered to match, so all three agree line for line.

### M-2 — §16.1 two-term active stop contradicts §16.3 and §25.6 three-term ratchet

§16.1: `ACTIVE_STOP = max(Initial_Stop, Trailing_Stop)`. §16.3 and §25 step 6: most
protective of `{initial, breakeven, trailing}`. §16.1 is the section an implementer will
copy, and it silently drops the breakeven candidate.

**Fix:** §16.1 restated as the three-term ratchet, matching §25.6.

### M-3 — Breakeven has no activation rule; `BreakevenActivationR` is used but never defined

`BreakevenActivationR` appears in §38 (validation), §25 step 3 ("if MFE crosses
threshold"), and roadmap Stages 9d and 12 Group C. It is never defined in §16.3, never
listed in §32, and §16.3 gives only the candidate-stop *price*, not *when* it arms.

**Fix:** §16.3 gains an explicit activation rule symmetric with §16.2's trailing
activation, and the parameter is added to §32.

### M-4 — "MFE crosses threshold" is unitless; MFE_R is never defined

§16.2 expresses trailing activation in R (`TrailingActivationR, e.g. +1R`). §25 steps 3
and 4 test "MFE crosses threshold". MFE is logged in §26 but never given units, and no
section converts an MFE price excursion into R.

**Fix (§16.2a, v0.7):**

```
Long:  MFE_R = (HighestPriceSinceEntry − Entry_Price) / (Entry_Price − Initial_Stop)
Short: MFE_R = (Entry_Price − LowestPriceSinceEntry) / (Initial_Stop − Entry_Price)
```

Denominator is the **initial** stop distance and is frozen at entry — it must not track
`ACTIVE_STOP`, or R inflates as the stop ratchets and both activation thresholds drift.

### M-5 — §10.5.A abandonment uses an unbuffered level; §5.2 invalidation uses a buffered one

§5.2 invalidates HTF structure at `HTF_Close < Protected_Low − Structural_Break_Buffer`.
§10.5.A abandons a setup on "a confirmed LTF close beyond the frozen protected level
itself" — no buffer. Whether that asymmetry is intentional (a tighter, faster setup-level
reset) or an oversight is not stated, and it produces a live window in which the setup is
abandoned but HTF structure is still `BULLISH`.

**Fix:** the asymmetry is *kept* — it is the defensible reading, since a setup is cheap
to re-form and structure is not — but §10.5.A now says so explicitly and cross-references
§5.2 so no implementer "helpfully" adds the buffer for consistency.

### M-6 — §11.1 contains a dangling self-reference in place of the actual BOS conditions

> `(plus setup-low/pullback/invalidation conditions from §11 in prior versions, unchanged)`

§11 pointing at §11 is circular, and "in prior versions" makes v0.6 non-self-contained
for a section that defines the entry trigger.

**Fix:** conditions enumerated inline in §11.1 — a valid setup must exist per §10.1, the
setup low must be established and unbroken, the setup must not have been abandoned per
§10.5, and the break candle must be strictly after the setup-low bar. §11.2 gets the
mirror written out rather than "Mirror", including the definition of `StructuralLow`,
which §16.5a references but which no section defines.

### M-7 — §7.2 presents `AMBIGUOUS` as a REGIME_STATE value

§2 and §7.3 give `REGIME_STATE ∈ {STRONG, ACCEPTABLE, CHOPPY}`. §7.2 lists `AMBIGUOUS`
in the same column as the other three, when it is a *band* of ER that resolves via ADX
into `ACCEPTABLE` or `CHOPPY`. An implementer following §7.2 literally adds a fourth
enum value that §7.3's permission test does not handle.

**Fix:** §7.2 reformatted so the ER bands and the resulting states are visibly distinct,
with the enum stated once and `AMBIGUOUS` named as a band.

### M-8 — Roadmap "6-parameter calibration budget" contradicts PRD §28 and Stage 12

Roadmap Stage 3 says ER_LOW/ER_HIGH are "first of the 6-parameter calibration budget".
PRD §28 says "~6-7 calibrated, rest fixed defaults". Stage 12's Groups A–D then list 13+
parameters to optimize. The stated budget and the actual plan differ by 2×.

**Fix:** roadmap Stage 12 now distinguishes the **calibration budget** (the 6–7
parameters swept for optimization and subjected to §28.1 stability testing:
`ER_LOW`, `ER_HIGH`, `LocationThreshold`, `BOS_ATR_Multiplier`,
`ROC_STRONG_THRESHOLD`, `TrailingActivationR`, `MaxRetracementBars`) from parameters that
get a **sanity-tested fixed default** and are deliberately not optimized. The Group A–D
tables mark each parameter as one or the other.

### M-9 — §14/§10.4 never name the signal price series

§10.4 requires "one consistent price series throughout" without saying which; §14 says
execution uses Ask (long) / Bid (short). MT5 chart bars are Bid-based by default but the
tester can be configured otherwise, and an implementer choosing Ask-based bars for signals
gets different swing points, different ATR, different BOS timing.

**Fix:** §10.4 pins the signal series to **Bid-based OHLC** (standard MT5 chart series)
for every structural and indicator computation, with execution on Ask/Bid per §14 and the
spread accounted for per §19/§21.

### M-10 — §38 validation list has gaps that permit undefined runtime behaviour

Missing checks for parameters the spec relies on:

- `HTF` must be strictly higher than `LTF` (§3 assumes it; nothing enforces it — an
  inverted pair makes the §4.4 freeze meaningless and the funnel silently empty)
- `ER_Lookback < 2` (the §7.1 sum is empty at `N < 1`, degenerate at `N = 1`)
- `ROC_Period < 1`
- `LTF_ATR_Period < 1`, `HTF_ATR_Period < 1`
- `Structural_Break_ATR_Multiplier <= 0` (see B-5)
- `ShadowLookbackBars < 1` (see B-6)
- `MaximumAllowedSpread <= 0`, `MaximumNormalizedSpread <= 0`
- All three `*_MinimumPoints < 0` (see B-4)

**Fix:** §38 list extended; every check has a named parameter in the log message, per
§38's own diagnosability requirement.

## Editorial findings

### E-1 — §9 has no subsections 9.1–9.3, but §37 references "§9.3"

§9's body (relevant level / Distance / NormalizedDistance / validity test) is unnumbered,
then jumps to 9.4 and 9.5. §37 cites "normalization (§9.3)" — a reference to a section
that does not exist. **Fix:** body numbered 9.1, 9.2, 9.3.

### E-2 — §12 has no subsections 12.1–12.3, but the roadmap references "§12.1–12.4"

Same defect: §12's body is unnumbered, then jumps to 12.4. Roadmap Stage 7 cites
"§12.1–12.4". **Fix:** body numbered 12.1 (classification), 12.2 (confidence/risk
mapping), 12.3 (threshold assignment requirement).

### E-3 — §17.1 contains unfinished editorial text

> `(boundary defined in §36.4/§37... see §36.4 in prior version, retained as the day-boundary rule: broker server 00:00 rollover)`

§37 is the ATR specification and has nothing to do with day boundaries. **Fix:** reduced
to a clean cross-reference to §36.4.

### E-4 — §34 references "§34 in the prior version"

A section referencing itself in an earlier draft. **Fix:** the recommendation is stated
directly.

### E-5 — Dangling references to sections that do not exist in this document

`§18.1` (cited by §18 and §39 test #4), `§28.1` and `§28.3` (cited by roadmap Stage 12),
and "§7 background" (cited by roadmap Stage 3 for the decile-bucket calibration process)
are all referenced but never written — each carried by an "unchanged from v0.5" note that
leaves v0.6 non-self-contained. **Fix:** all four written out as real subsections.

### E-6 — §29 "Version 1 Scope — Unchanged from v0.5"

The scope of v1 is load-bearing (it is what §8 partially describes and what Stage 13
tests against) but is not stated anywhere in this document. **Fix:** scope written out
explicitly as in/out lists.

### E-7 — Roadmap summary table is malformed

The Stage 4 row has its two right-hand columns merged into one cell, and Stages 9–13 have
`(managing)` in the *"First real trades appear?"* column — a value that answers a
different question than the column header asks. **Fix:** table rebuilt with a consistent
`Trades appear?` column (`No` / `Yes` / `Yes (refining)`) and every row given its own
zero-trade risk factor.

## Non-findings — checked and correct

Recorded so they are not re-litigated in the next review:

- **§7.1 ER index arithmetic.** With `Close[0]` most-recent, the denominator `Σ(i=1..N)
  |Close[i-1] − Close[i]|` correctly spans the same `N` intervals as the numerator
  `|Close[0] − Close[N]|`. Correct as written.
- **§7.2 ER band coverage.** `ER >= ER_HIGH`, `ER < ER_LOW`, `ER_LOW <= ER < ER_HIGH` are
  exhaustive and mutually exclusive given §38's `ER_HIGH > ER_LOW` check. No gap, no overlap.
- **§12 tier coverage.** `>= STRONG`, `<= NEGATIVE`, and the open interval between are
  exhaustive and mutually exclusive given §38's `ROC_STRONG_THRESHOLD >
  ROC_NEGATIVE_THRESHOLD` check.
- **§16.5a short-side direction.** `Short: Close > StructuralLow` is the correct mirror —
  a bearish BOS breaks *below* `StructuralLow`, so the failed-breakout condition is a
  close back *above* it. (The only defect here is that `StructuralLow` itself is
  undefined — covered by M-6.)
- **§25 exit-before-MFE ordering.** Checking exits against the previous bar's `ACTIVE_STOP`
  before updating MFE with this bar's high/low is deterministic and intentional: it avoids
  the intrabar path ambiguity of "did the stop get hit before or after the new extreme".
  Correct, and now stated as a rationale note rather than left implicit.
- **§17.3 cooldown release.** Condition 5 (`BOS_ID != LAST_TRADED_BOS_ID`) is implied by
  conditions 3 and 4, but it is a cheap, explicit backstop against a reference-level
  comparison that is subtly wrong. Kept as-is.
- **§4.1 tie-breaking.** Strict inequality on both sides, with neither tied bar qualifying,
  is unambiguous and correctly worked through in the document's own `100, 102, 102, 99`
  example.
